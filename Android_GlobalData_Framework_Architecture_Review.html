01

方案概述与设计结论

统一访问接口，三种独立数据托管后端

由 Apps 业务层 → GlobalDataManager 客户端 SDK → Binder/AIDL → GlobalDataService 系统服务 构成统一数据访问链路。GlobalDataService 按 App 选择路由到 MemoryBackend、FileBackend、DatabaseBackend，统一执行访问控制、原子变更、版本管理和通知分发。

需要冻结的核心基线： App 新增一个全局基本类型或可序列化引用类型对象，只调整该 App 的业务模型、Key 与 Codec，不修改客户端 SDK、AIDL 或 GlobalDataService，不因新增模型重新编译 AOSP。

这三类存储是互相独立的数据空间，不是“先写内存、再自动刷入文件或数据库”的三级缓存。除非将来显式引入镜像/同步策略，否则相同 namespace + key 在三种存储中可以拥有不同的值。

Apps 层只关注什么？

声明 namespace/key、创建值或 Java 类、选择存储方式、调用 put/get/update/remove、注册或撤销 Observer。

Service 层统一负责什么？

鉴权、数据路由、字节值托管、持久化提交、版本校验、跨进程通知、资源与生命周期管理。

设计原则

业务模型零侵入

服务不引用任何业务 Java 类，不因新增字段或新对象编译 Framework。

存储方式显式选择

App 自己选 Memory / File / Database，服务只执行约定语义。

统一能力，独立实现

三个 Backend 各自优化，但对外遵循相同 CRUD + 事件协议。

Backend 建议实现

MEMORY

MemoryBackend

使用 Map + 锁或原子计算，托管序列化数据。为满足“本次开机保留”，不应使用会自动淘汰权威数据的普通 LRU 缓存；应通过容量配额、显式删除与拒绝超额写入控制占用。

FILE

FileBackend

按 namespace 维护 AtomicFile + Proto/二进制映射。可内存加载快照加速读，但每次声明成功的持久化写入必须先完成可靠文件提交。适合小数据、低频更新。

DATABASE

DatabaseBackend

SQLite + WAL + KV 表，事务提交，支持单键读写、版本控制；未来如需条件查询、集合和批处理，可继续扩展专用数据库能力。

性能选型不是绝对排序：Memory 通常避免磁盘 I/O，但仍有 Binder 开销；File 和 SQLite 的效率取决于键值大小、读写频率、事务批量、文件重写大小及存储设备。具体阈值应通过目标硬件 Benchmark 决定。

存储示例路径建议划分为设备加密（DE）与凭据加密（CE）区域，具体路径、访问时机和 SELinux 文件类型需按 AOSP 产品分支确定，不将示意路径当作固定契约。

05

客户端 SDK 设计与使用范式

统一入口、统一操作方法、业务新增零改动

统一选择存储方式

JAVA · API PROPOSALGlobalDataManager manager =
        context.getSystemService(GlobalDataManager.class);

GlobalStore memory   = manager.memory("device");
GlobalStore file     = manager.file("device");
GlobalStore database = manager.database("device");

不同 Store 的 put/get/update/remove/observe 操作保持一致；device 是逻辑 namespace，而不是用户可传入的真实文件路径。

基本类型与持久化使用

JAVA · APPS LAYER// ① 内存托管：本次系统运行期共享
memory.putInt("device_mode", 1);
int mode = memory.getInt("device_mode", 0);
memory.putInt("device_mode", 2); // 更新

// ② 文件托管：已提交的数据重启后保留
file.putBoolean("boot_animation", true);
boolean enabled = file.getBoolean("boot_animation", false);

// ③ SQLite 托管：已提交的数据重启后保留
database.putLong("device_count", 100L);
long count = database.getLong("device_count", 0L);

database.remove("device_count"); // 删除

建议冻结的核心 GlobalStore API

JAVA · INTERFACE SKETCHinterface GlobalStore {
    boolean contains(String key);
    long putInt(String key, int value);
    int getInt(String key, int defaultValue);
    long putLong(String key, long value);
    long getLong(String key, long defaultValue);
    long putBoolean(String key, boolean value);
    boolean getBoolean(String key, boolean defaultValue);
    long putFloat(String key, float value);
    float getFloat(String key, float defaultValue);
    long putDouble(String key, double value);
    double getDouble(String key, double defaultValue);
    long putString(String key, String value);
    String getString(String key, String defaultValue);
    long putBytes(String key, byte[] value);
    byte[] getBytes(String key);

    <T> long putObject(String key, T value, ValueCodec<T> codec);
    <T> T getObject(String key, ValueCodec<T> codec);
    <T> long updateObject(String key, ValueCodec<T> codec,
                          UnaryOperator<T> updater);

    DataSnapshot readSnapshot(String key);
    long putIfRevision(String key, EncodedValue value,
                       long expectedRevision);
    long remove(String key);

    Subscription observe(String key, Executor executor,
                         ChangeListener listener);
}

上述代码为评审用 API 草案，不是可直接复制到 AOSP 编译的完整源码。DataSnapshot、EncodedValue、Subscription 等模型将在接口冻结后正式定义。

创建/修改语义：put() 是 upsert（不存在则创建，存在则替换）；若必须保证“只创建不覆盖”，建议补充 putIfAbsent()。并发对象修改使用 putIfRevision() / updateObject()，避免丢失更新。
06

Java 引用类型对象托管

Codec 位于 Apps 层；服务只持有字节快照，不持有业务类实例

引用类型可以是普通 Java POJO、嵌套对象、List、Map 等可序列化数据。GlobalDataService 不需要加载、反射或识别业务对象的 Class，也不能跨进程保持同一个 Java 对象引用。

JAVA · MODEL & CODECpublic class DeviceConfig {
    public int deviceId;
    public String deviceName;
    public boolean enabled;
}

// 在 SDK 中一次定义；各 App 按业务模型提供 Codec。
public interface ValueCodec<T> {
    String schemaId();
    int schemaVersion();
    byte[] encode(T value);
    T decode(byte[] payload, int savedVersion);
}

同一对象可托管在任意 Store 中

JAVA · APPS LAYERDeviceConfig config = new DeviceConfig();
config.deviceId = 1001;
config.deviceName = "Android TV";
config.enabled = true;

ValueCodec<DeviceConfig> codec = /* App 自己实现 JSON/Proto Codec */;

memory.putObject("runtime_config", config, codec);
file.putObject("saved_config", config, codec);
database.putObject("db_config", config, codec);

DeviceConfig fromMemory = memory.getObject("runtime_config", codec);
DeviceConfig fromFile = file.getObject("saved_config", codec);
DeviceConfig fromDb = database.getObject("db_config", codec);

// 注意：修改 fromMemory 的字段不会自动修改 Service 内的数据
fromMemory.enabled = false;
memory.putObject("runtime_config", fromMemory, codec);

统一的序列化数据契约

字段用途约束 / 评审关注点
storeTypeMemory / File / Database 路由固定枚举，不能随业务类扩展
userScope区分用户级与设备级数据与权限绑定，不能相信调用方自报
namespace + key逻辑数据身份权限隔离、长度、字符集与唯一性
valueType基本类型或 BYTES固定、可扩展、类型不匹配应明确报错
schemaId + schemaVersion引用类型格式身份由 Apps 协商并处理版本升级
payload实际编码后的字节值最大大小、拷贝策略、恶意输入边界
revision / epoch并发控制和重启识别持久化与内存版本语义分别定义
对象变更不会被自动观察：没有经过 GlobalStore.putObject() / updateObject() 的原地字段修改，仅发生在客户端 Java 堆中，不会写回 Service，也不会触发 Observer。updateObject() 的回调可能因 CAS 冲突执行多次，不应包含不可重复的副作用。

跨 App 读取同一引用类型对象，需要事先约定相同的 schemaId、兼容的数据编码格式和版本迁移策略。服务无法凭字节自动恢复一个它从未认识的任意 Java 类。

GlobalDataService 内部模块

服务稳定、业务模型不侵入、Backend 可独立演进
模块主要职责建议约束
GlobalDataBinder稳定 AIDL IPC：get / put / remove / observer严格参数校验，禁止透传任意 SQL
AccessController校验 UID、用户、签名、namespace ACL在每个读写/订阅入口检查
StorageRouter按 StoreType 路由到三个 Backend不得产生后端间隐式同步
MemoryBackend托管内存字节快照与修订版本容量配额、线程安全、不意外淘汰
FileBackendAtomicFile/Proto 的小规模持久化 KV原子写入、损坏恢复、schema 演进
DatabaseBackendSQLite/WAL、事务及键值查询升级迁移、索引、异常恢复
RevisionManagerCAS、版本号与服务 epoch比较与替换必须原子化
ObserverManager订阅筛选、异步事件投递、死亡清理不可持锁执行远程回调

统一 Backend 合约

JAVA · INTERNAL INTERFACEinterface StorageBackend {
    DataSnapshot get(StoreKey key);

    // expectedRevision = -1 表示无条件 upsert
    // expectedRevision = 0 表示仅在不存在时创建
    long put(StoreKey key, EncodedValue value,
             long expectedRevision);

    long remove(StoreKey key, long expectedRevision);
    long getRevision(StoreKey key);
}

// StoreKey 由 (userScope, storeType, namespace, key) 构成。
// EncodedValue 由 (valueType, schemaId, schemaVersion, payload) 构成。

AIDL 协议建议

AIDL · CONCEPTUAL CONTRACTinterface IGlobalDataService {
    DataSnapshot get(int storeType, String namespace,
                     String key);

    long put(int storeType, String namespace, String key,
             in EncodedValue value, long expectedRevision);

    long remove(int storeType, String namespace,
                String key, long expectedRevision);

    void registerObserver(int storeType, String namespace,
                          String key, IGlobalDataObserver observer);

    void unregisterObserver(IGlobalDataObserver observer);
}

上述 AIDL 是接口形态草案。真正编译时需为 DataSnapshot、EncodedValue 等定义可 Parcel 化的数据结构；还需纳入 UserScope、授权与异常约定。

建议的持久化实现

文件型：一个 namespace 一个小型映射文件（或受控文件分片），数据序列化后通过 AtomicFile 可靠替换。数据库型：一个或按用户拆分的 SQLite 库，典型 KV schema 包括 namespace、key、valueType、payload、schemaVersion、revision，并通过事务提交。

默认同步写入接口应在存储提交成功之后返回，并且不在 system_server 主线程执行磁盘 I/O。对高频场景可另外提供批处理接口，避免大量小事务与 Binder 往返。

08

变更通知、版本与并发

三种 Backend 共用 ObserverManager
JAVA · APPS LAYERGlobalStore memory = manager.memory("device");

Subscription subscription = memory.observe(
    "runtime_config",
    context.getMainExecutor(),
    event -> {
        DeviceConfig latest = memory.getObject(
            "runtime_config", codec);
        updateUi(latest);
    }
);

// 在应用组件生命周期结束时
subscription.close();

一次写入的完整流程

STEP 01App 调用 GlobalStore.put / update
STEP 02Binder 接入 + UID / namespace 鉴权
STEP 03StorageRouter 选择唯一 Backend
STEP 04原子替换或持久化事务完成
STEP 05生成 revision，投递变更事件
STEP 06订阅者读取最新快照并更新 UI
事件字段含义
storeTypeMEMORY / FILE / DATABASE
userScope用户级或设备级数据范围
namespace / key发生变化的具体数据
operationCREATE / UPDATE / DELETE
revision本数据的新版本，用于乐观并发与过期检测
epoch系统服务运行实例；内存版本重置后可识别服务重启

并发更新：读取返回 DataSnapshot(value, revision)；修改时携带预期版本。若版本冲突，服务拒绝覆盖，SDK 可重新读取并重试。这里对对象的修改发生在 App 进程，Service 只原子提交新字节快照。

通知保证：成功提交后通知已注册且有权限的客户端；通知是“数据可能已变化”的提示，不是可靠消息队列，不保证离线补投、每一次中间状态都能被观察。客户端应以重新读取最新快照为准，Binder 断线重连后重新注册并同步状态。

注册时的竞态处理：建议 SDK 提供订阅并获取首个快照的组合能力，或采用“先注册监听 → 读取快照/版本 → 核对版本”的流程，避免刚启动就漏掉关键变化。

跨 App 权限、安全与隔离

全局可访问不等于所有 App 可无限制写入

所有读、写、删除和 Observer 注册操作必须由 GlobalDataService 校验真实 Binder 调用者身份。不要把客户端传入的 UID、PackageName 或 userId 当成可信身份来源。

Namespace 示例建议默认访问说明
system.*受信任系统组件、签名级策略保护系统内部配置、禁止普通 App 越权
app.<owner>.*仅所有者读写普通应用私有共享存储空间
public.<owner>.*其他 App 经策略允许读取；所有者写入公开共享仍需用户隔离与配额
shared.<team>.*显式 ACL / 预置可信策略业务协作式跨 App 读写，可作为扩展
安全设计待评审：仅用数字 UID 表达持久化 namespace 所有权并不充分，卸载后 UID 可能复用。建议将 namespace 所有权绑定经验证的包身份及签名证书，明确重装、签名轮换、shared UID、多用户及卸载清理策略。

最小安全控制

  • Namespace 创建与授权采用统一规则，不为每个新业务 Key 修改 AOSP 权限代码。
  • 隔离 Android 多用户 / 工作资料；设备级共享数据必须显式授权。
  • 支持 DE / CE 数据范围：开机未解锁时可用的数据与用户解锁后数据分开。
  • 限制单条 payload、每 UID 总存储量、内存占用、Observer 数、写入频率和批量大小。
  • Service 在 system_server 内运行，要强化输入校验，避免 OOM、阻塞系统关键线程和异常扩散。

建议 V1 讨论单值 64 KiB 作为默认软上限（具体值待压测确认）。大对象传输需要文件描述符或共享内存等额外协议，不应简单无限放大 Binder 数据报文。

关键风险、取舍与非目标

评审中应主动确认而非默认为已解决
风险 / 取舍影响处理建议
system_server 资源竞争写入阻塞、内存膨胀影响系统专用 I/O 执行器、严格容量与频率配额；考虑未来隔离存储进程
FileBackend 写放大大映射文件高频更新性能差限定文件后端数据量，频繁写入建议 DB
Binder 数据上限大对象传输失败或拖慢系统单值限制，必要时 FD / SharedMemory 独立传输
对象 schema 变化旧数据反序列化失败schemaId/version + Codec 升级与迁移策略
并发丢更新多个 App 修改同一对象覆盖彼此CAS / revision / 幂等重试
事件遗漏与观察竞态客户端缓存滞后重新读取为真值；重连重新同步；版本检查
权限与所有权滥用跨 App 泄漏、非法修改包签名身份、用户隔离、ACL、配额、审计
持久化损坏与升级数据无法读取或历史数据丢失AtomicFile 恢复、SQLite 迁移与备份/恢复策略

V1 明确不承诺

  • 不支持跨进程共享同一 Java 对象引用：传输的是序列化快照。
  • 不自动追踪对象字段变化：赋值和修改必须显式调用 SDK。
  • 三种存储不自动相互同步：各自独立。
  • Observer 不是可靠消息队列：不承诺离线通知补投。
  • 不允许向普通 App 暴露任意 SQL：数据库后端先提供统一 KV；复杂查询以后单独定义。
  • 不承诺 MemoryStore 异常恢复：system_server 重启后 Memory 值会丢失。

需要团队拍板的关键决策

当前为提议，不应误认为这些设计已经定稿
D-01 · SDK 面向哪些 App 公开？待定

只给系统预装 App，还是提供定制 SDK 给普通第三方 App？影响 API 兼容、权限与维护成本。

D-02 · namespace 所有权待定

系统固定空间 + App 自动空间 + 显式授权空间如何命名与持久化？包证书、卸载和 UID 复用如何处理？

D-03 · DE / CE 与跨用户范围待定

哪些数据设备级共享？哪些数据按用户隔离？文件与数据库是否按用户物理分区？

D-04 · FileBackend 物理格式待定

AtomicFile + Proto 快照是否作为 V1 首选？单 namespace 文件大小和写频率阈值是多少？

D-05 · DatabaseBackend 功能边界待定

V1 只做 SQLite KV，还是直接增加 collection/分页/批处理事务接口？

D-06 · 数据大小与配额待定

单键上限、每 App 的 Memory/File/DB 上限、Observer 数量、操作频率。

D-07 · 通知可靠性契约待定

确认 best-effort / 只传元数据 / 重读最新值；是否要提供注册 + 快照原子接口？

D-08 · 服务部署位置待定

V1 放 system_server；未来若高频使用或第三方可写，是否把 Backend 隔离到独立系统进程？
