架构决策摘要

在首次 AOSP 集成后，冻结最小公开 Bridge + 通用 IPC，业务类 / Codec / DataKey / Repository 放到可独立发布的 SDK；GlobalDataService 只管理不透明的字节值、访问权限、版本与通知。Memory、File、SQLite 彼此独立，EventBus 不落盘。业务扩展更新 SDK 与 APK，不改 system_server；新增底层能力仍遵循平台升级边界。

适用：平台架构师 · Framework/AOSP 开发 · App/SDK 开发 · 安全与测试评审

01｜定位与状态

本最终 v2 文档合并两版后续设计中仍适用的内容，并按当前仓库源码校正。它面向可修改 AOSP 的定制 Android 设备，描述三种托管存储、独立的无载荷事件通道、可随 App 更新的 SDK，以及首次系统集成边界。原始需求初稿另行保留。

内容当前状态
系统服务、三 Backend、ACL、DataObserver、EventHub仓库有增量 Java/SELinux 源码；尚未在目标 AOSP/厂商源码中完成系统构建和设备验收。
IPC、Client、Contracts、App1/App2仓库有独立 Gradle 工程和示例调用；具体本地构建结果应以运行记录为准。
重启、断电、跨用户、平台签名、SELinux属于目标设备验收，不能由源码审阅或主机 JVM 测试推定通过。

下文的“当前实现”指仓库代码具备相应逻辑，不等于已在定制系统镜像上实测。业务新增 Key、Codec、POJO 或 Topic 的升级边界成立于底层 IPC 契约保持兼容且目标设备已完成首次集成的前提下。

03｜地址、类型与传输契约

DataKey<T> 固定 Store、Scope、owner 包、namespace、key 与 ValueCodec<T>。服务端还从真实 Binder UID 推导 User ID。Store 参与定位，同名 Key 在 Memory、File、Database 中是三份独立数据。EventTopic 只有 Scope、owner 和完整 topic，不属于任何 Store。

Codec 在 App 侧将值编码为 schemaId、schemaVersion、encoding 和 byte[]；服务端只保存不透明字节。单值 payload 上限为 64 KiB。读取时 Client 先匹配 schema ID，再按存储版本解码。原 String 集合使用 JSON/UTF-8，新增数值/布尔集合使用各自版本 1 的长度前缀二进制格式。

当前协议版本为 1.1。IGlobalDataTransport、IDataObserver 与 IEventListener 组成 Binder 协议；Client 初次连接时检查 major/minor、最大载荷和所需功能位。系统侧和 SDK 各有一份 AIDL 与 Wire，可用 verification/verify.ps1 比较声明和公开常量。

04｜三种 Backend 与四种生命周期

三种 Backend 使用同一类地址与读写接口，但数据互不自动镜像、迁移或回写。以下第四行是独立事件通道，不是第四种存储。

能力实现与位置生命周期及承诺
Memorysystem_server 内按 namespace 保存字节快照与高水位；每 owner 当前 payload 上限 4 MiB。App 退出后仍可访问；服务进程或设备重启后丢失。
File每 Scope/User/owner/namespace 一个 SHA-256 命名的 .gdf；AtomicFile、CRC32、缓存；文件上限 1 MiB。代码在文件提交后才报告成功；跨重启与断电恢复须在设备上验证。
Database每 Scope/User 一个 globaldata-v1.db；SQLite kv/nsrev、WAL、synchronous=FULL；每 owner 当前 payload 上限 16 MiB。代码在事务提交后才报告成功；设备持久化与故障恢复须验收。
EventHub内存中的在线 topic 订阅与待发送任务；无业务 payload。不落盘、不补发、不主动唤醒离线 App；服务死亡期间事件丢失。

File/Database 根据 Scope 写入系统 DE 或用户 CE 目录。DEVICE_DE 归一到 User 0；USER_DE、USER_CE 按调用者 User 隔离。CE 用户未解锁时返回 LOCKED。

05｜写入、CAS 与一致性

服务端存储队列串行执行写入，容量为 128；队列满返回 BUSY。put 是单 Key 无条件 upsert；putIfAbsent 只检查当前是否不存在；putIfRevision 用读取到的快照同时比较 revision 和服务 epoch。update 是 Client 的“读→计算→CAS”便利流程，冲突时最多重试 3 次，更新函数可能执行多次。

每个 Backend 为 namespace 保存单调递增的 revision 高水位。存在的 Key 返回自身 revision，不存在的 Key 返回 namespace 高水位。成功删除推进高水位；删除前的旧快照不能通过 CAS 复活该值。服务重启后 epoch 改变，也会拒绝旧快照。不同 Key 的提交可能推进同一 namespace 高水位，故不存在 Key 的 CAS 可能保守冲突。

File 的 AtomicFile 完成替换、Database 的 SQLite 事务完成后，服务才返回成功并排入数据通知。失败、权限拒绝及 CAS 冲突不应被当作成功通知。当前没有跨 Key、跨 Store 的原子事务接口；事件到达也不能代替写入结果确认。

06｜DataObserver：真实数据变化

DataObserver 订阅完整数据 Key，只有对应 Store 的真实提交才产生变化提示。提示包含地址、操作、revision 与 epoch，不直接承载业务对象。Client 的 observeAndRead 先订阅再读取当前快照；以后每次提示都重新读取权威当前值。因此连续提交可能合并为最终状态，回调次数不是写入次数。

服务端每 UID 最多 64 个数据订阅，通知队列容量 256；队列溢出时请求重同步。发送前再次检查 OBSERVE 权限，Binder 死亡时移除订阅。Client 检测到服务死亡后尝试重订阅并重读当前值；页面关闭时仍须关闭 Subscription 和 manager。需要重读值的订阅者应同时具备 OBSERVE | READ。

07｜GlobalEventBus：无载荷事件

这是从早期 v2 设计延续的独立通道：App 主动 post(topic)，服务校验 PUBLISH 权限和速率，再向当时在线、仍具 SUBSCRIBE 权限的订阅者转发。事件不创建 Memory/File/Database Key，不包含业务 payload，也不补发离线期间的消息。成功 Future 只表示入队成功，不保证每个订阅者实际收到。

双向示例流程

  1. App1 使用 DeviceTopics.app1ToApp2ConfigRefreshedEvent(false) 授予 App2 SUBSCRIBE；App2 先订阅，App1 再发布“配置已刷新”。
  2. App1 使用 DeviceTopics.app2ToApp1ConfigRefreshRequestEvent(false) 授予 App2 PUBLISH 并先订阅；App2 再发布“请求刷新配置”。
  3. 收到事件后若需要配置内容，接收方另用 DataKey 读取当前存储值。数据授权与事件授权分别管理。

服务端每 UID 每秒最多接受 20 次发布；事件队列容量 256，每 UID 最多 64 个事件订阅。队列满返回 BUSY。服务重启后 Client 重订阅，但不会重放停机期间的事件。

08｜身份、安全与授权

安全边界在系统服务。它从 Binder 获取真实 calling UID/User，核对 owner 包、当前签名、Scope 与资源授权；客户端传来的 owner 仅是地址，不能伪造身份。普通数据 namespace 只能是 share.<ownerPackage> 或 app.<ownerPackage>；普通事件 topic 以 events.<ownerPackage>/ 开头。sys.* 与 DEVICE_DE 要求系统 UID 或平台签名身份。

数据授权粒度为 Scope/User/owner/namespace，覆盖该 namespace 的三个 Store；事件授权粒度为完整 topic。READ、WRITE、DELETE、OBSERVE 与 PUBLISH、SUBSCRIBE 分开检查。owner 身份和目标包授权关联签名摘要，保存于 DE 下的 acl-v1.bin。目标包须已安装才能授权；重装后若签名变化，不继承旧授权。ACL 文件损坏时实现拒绝继续改写。

普通 App 不直接读取系统存储文件。BuildConfig.SYSTEM_SCOPE 仅改变示例地址，不授予平台身份；平台示例必须用目标系统平台密钥签名并在设备上验证。

09｜Client API 与最小使用流程

App 调用 GlobalDataSdk.connect(context) 获得 manager；Binder 在首次操作时连接。异步 API 返回 CompletableFuture，同一 manager 的 I/O 任务串行执行。readBlocking 和 putBlocking 拒绝主线程；Future 回调不保证在 UI 线程。组件结束时关闭订阅和 manager。

DataKey<Integer> key = DeviceDataKeys.memoryIntOperationCount(false);
GlobalDataManager manager = GlobalDataSdk.connect(context);
manager.grantData(key, DeviceDataKeys.APP2_PACKAGE, Wire.READ | Wire.OBSERVE)
       .thenCompose(ignored -> manager.put(key, 9999));
// App2：授权完成后订阅并读取；收到变化时 SDK 会重读当前快照。
manager.observeAndRead(key, callbackExecutor, listener);

此例选 USER_CE 与 App1 拥有的共享 namespace。先安装 App2，再由 App1 授权，两个 App 需处于同一已解锁用户且设备已集成服务。完整错误处理和页面步骤见客户端调用指南与演示目录。

10｜AOSP 接入与版本兼容

仓库的 aosp-patch/ 是按 Android 16 基线编写的增量源码，不是完整系统树。目标分支需集成公开 GlobalDataBridge.getTransportBinder()、三个 AIDL、系统服务启动与 SELinux 规则；普通 App 不能靠反射隐藏 ServiceManager 接入。bridge-stubs 只供本地编译，平台公开 API 应与真实 OEM SDK 桩核对。

当前 Client 要求协议 major=1、minor 至少为 1，并检查所需功能位。业务 schema 版本与 IPC 版本分别演进：旧值能否被新旧 App 共同读取由共享 Codec 契约决定，不由系统服务理解业务字段。业务变更只更新 AAR/APK 的前提是现有传输字段及系统能力足够；底层协议改动需同步系统侧并重建镜像。

工程配置为 API 36、Java 17、AGP 8.6.1；SDK Wrapper 为 Gradle 8.7，App1/App2 Wrapper 为 Gradle 8.13。AOSP 编译、刷机与验收命令见接入指南。

11｜限制、故障与运维

服务端单值上限 64 KiB；Memory 当前 payload 每 owner 4 MiB，File 每 namespace 文件 1 MiB，Database 当前 payload 每 owner 16 MiB。存储任务队列容量 128，数据通知和事件队列各为 256。Client 异步 API 适合界面调用；连续异步操作应组合 Future，避免在同一 manager 的回调中阻塞等待新任务。

不存在、冲突、权限拒绝、CE 锁定、配额、协议不支持、存储不可用及队列忙等状态由 Wire 定义，Client 通过 GlobalDataException.status 暴露。订阅 AIDL 失败仅返回 -1，Client 目前统一映射为 PERMISSION_DENIED；排障时不能仅凭该状态区分权限与订阅数量上限。

当前仓库没有目标设备压测或生产监控数据，文中限额是实现常量而非吞吐或时延 SLA。上线前需测写入延迟、队列积压、存储空间不足、数据库错误、回调风暴与进程恢复。
