架构决策摘要

在首次 AOSP 集成后，冻结最小公开 Bridge + 通用 IPC，业务类 / Codec / DataKey / Repository 放到可独立发布的 SDK；GlobalDataService 只管理不透明的字节值、访问权限、版本与通知。Memory、File、SQLite 彼此独立，EventBus 不落盘。业务扩展更新 SDK 与 APK，不改 system_server；新增底层能力仍遵循平台升级边界。

适用：平台架构师 · Framework/AOSP 开发 · App/SDK 开发 · 安全与测试评审

01｜文档定位、目标与边界

目标：面向可修改 AOSP 的定制 Android 设备，建设一个系统级跨 App 数据托管基础设施。所有经过授权的普通 App、Settings、Launcher、SystemUI 及 Framework 组件，可通过同一套 SDK 管理三种存储与两种通知能力；新的业务对象、类型安全接口或事件主题只需更新相应 App / SDK，不随业务数据变更修改 system_server。

本设计的关键判断：v2.1 的核心收益不是把 MemoryStore 改成另一种容器，也不是让 FileStore 取代 SQLite，而是把 “稳定的系统级数据托管能力” 与 “可持续升级的业务数据契约” 彻底分离。

1.1 设计范围

类别 必须支持 明确说明
MemoryStore 基本类型 / Java 对象的创建、读取、修改、删除、监听 只承诺服务进程存活期；设备重启后不恢复
FileStore 同一套 CRUD / Observer API AtomicFile + Proto/二进制 KV，适合低频配置，跨重启持久化
DatabaseStore 同一套 CRUD / Observer API SQLite + WAL + KV，适合频繁写入和大量 Key，跨重启持久化
GlobalEventBus 无业务载荷的跨 App 事件发布、订阅、注销 事件不创建任何 Store 记录，不做历史重放
引用类型 POJO / List / Map / 自定义对象 客户端 Codec 编码成字节；Service 不直接持有业务 Java 对象
SDK 演进 通用 SDK + 业务 Data SDK 分开发布 不需要重新编译 AOSP；依赖静态 AAR 的 App 仍需更新 APK

1.2 不在 v2.1 范围内

  • 不是跨进程共享同一个 Java 对象引用。get() 返回值副本；字段的本地修改不会自动写回。
  • 不是给普通 App 提供任意系统数据访问权；不同 UID、Android User / Profile 要按 ACL 隔离。
  • 不是任意 SQL 代理。DatabaseStore v2.1 首先实现受控 KV；关系查询是独立扩展议题。
  • 不是可靠离线消息队列。GlobalEventBus 不拉起离线 App、不补发历史事件。
  • 不是“所有 SDK 修改都无需系统升级”。新底层操作或权限能力超出旧 IPC 契约时仍可能需要系统更新。

1.3 文档适用与状态

本稿按 Android 14–16 类似架构的定制 AOSP 分支提出可落地的详细设计。具体源码位置、构建参数、SELinux 策略和 API 暴露方式，需要在目标分支验证。所有 Java / AIDL 片段均为接口或算法示例，不是已编译测试通过的完整补丁。建议先冻结接口协议，再按文末测试矩阵实现。

02｜基线需求与可验收条件

验收基线中最严格的一条：在同一台已经刷入 v2.1 系统服务的设备上，保持 frameworks/base、system_server 和平台镜像二进制不变，只发布新的 device-data-sdk 及 App1/App2 APK，完成一个全新 DeviceConfigV2 对象的三种 Store 读写、监听和 EventBus 新 Topic 测试。新功能必须完全依靠首版已经支持的 IPC 能力。

03｜相对 v2.0 的架构变化

主题 v2.0 已有方向 v2.1 正式约束 为什么更好
客户端代码 独立 AAR Client SDK 与各业务 Contracts SDK 分离 业务模型不污染通用 SDK
业务类 允许封装 SDK 类型化 DataKey<T> + Repository 避免字符串 Key、Store 选择、Codec 四处重复
服务端能力 三 Backend + EventHub 稳定的、仅识别 byte[] 的传输契约 新业务类无需修改服务端
错误处理 多为异常建议 结构化状态码 + capability 不同 SDK/服务版本可预测地协作
并发控制 revision / CAS 保留删除 tombstone，拒绝 ABA 防止删除重建后误用旧版本覆盖
Observer 支持重连 SDK 自动重订阅 + 初始化快照规则 减少业务层漏变更窗口
权限 Namespace ACL 显式 Owner 身份 + READ/WRITE/OBSERVE 区分 防止 UID 复用或监听越权
发布 不重新编 AOSP 发布矩阵与兼容测试 明确 AAR 变更仍需 APK 重新集成

需要防止的过度设计：不需要将 DeviceConfig 加入 bootclasspath，不需要按业务类型增添 AIDL 接口，不需要让 SystemService 注册 Java ClassLoader，也不需要每增加 Key 就改系统权限表。

4.1 必须保持的依赖方向

Apps → Business Data SDK → GlobalData Client SDK → Stable IPC Bridge/Transport → GlobalDataService → StorageBackend

  • Apps 层可依赖通用 SDK 或业务 SDK，但不依赖 system_server 内部类。
  • Business Data SDK依赖 Client SDK 的 DataKey / Codec 抽象，不依赖 AOSP 内部类，也不在服务端运行。
  • Client SDK负责 Java 类型和 byte[] 转换、CAS 重试、订阅生命周期、错误映射；只依赖被公开支持的 Bridge 或受控 Gateway。
  • Bridge/IPC不包含任何 DeviceConfig、UserProfile 等业务类。
  • Service仅处理 StoreKey、EncodedValue、revision、ACL、事务、通知；禁止 App 上传可执行 ClassLoader 代码。

4.3 部署形态建议

默认基线 A（最简 AOSP 集成）：GlobalDataSystemService 运行在 system_server，三个 Backend 和 EventHub 也在该进程，但 I/O 必须在专用线程执行；对非受信任 App 限额、限速。优点是启动路径较清晰；缺点是存储引擎问题可能影响关键系统进程。

增强形态 B（大量第三方 App / 强隔离要求）：保留首次系统集成的稳定 Bridge，托管引擎迁移到专用受信任系统进程，客户端直接通过该进程 Binder 通道访问并由服务端验证真实调用 UID。不能简单通过 system_server 代理全部 IPC 后仅根据 Binder.getCallingUid() 鉴权，因为那会把转发请求的 UID 变成中间进程 UID。B 需要独立的启动时序、SELinux 与服务注册设计。

本稿技术实现与验收以形态 A 为参考，B 作为后续按威胁模型和压力测试结果决定的部署选项。系统最早启动阶段确需访问数据时，优先保证可用时序，再考虑进程外移。

5.1 分层边界的工程规则

  1. 不能让业务 SDK 直接依赖 AOSP 内部 com.android.server.* 包。
  2. 不能把 com.oem.globaldata.ipc.* 同名类在 App 的 AAR 中打包两份；IPC 生成代码要来自同一套冻结的 AIDL 源，避免重复类与 descriptor 不一致。
  3. 不能把需要频繁升级的业务 API 放入定制的公开 Framework API txt；公开 Bridge 保持极小。
  4. 不能由客户端仅凭用户传入字符串伪造 owner/UID；命名空间归属由服务端真实身份解析。
  5. 通用 Client SDK 通过内部 Maven 仓库发布，使用语义化版本和兼容性测试，避免手工复制多个 AAR 到不同 App。

5.2 业务 SDK 的必要性

对于只有一个 App 使用的数据，可直接在该 App 定义 DataKey/Codec；对多个 App 共用的数据协议，应该将 POJO、Codec、Key、Topic 和 Repository 一起放在独立 Business Data SDK。SDK 升级不会热更新所有已安装 App；依赖静态 AAR 的 App 必须构建并分发新 APK 才获得新代码。旧 APK 可以继续运行，只要数据 schema 和 IPC 兼容。

06｜客户端 SDK：通用 API 与类型安全调用

6.1 核心 API 建议

// 伪代码：用于接口冻结与职责评审，不是完整 Java 类
public interface GlobalDataManager {
    <T> DataSnapshot<T> read(DataKey<T> key);
    <T> WriteResult put(DataKey<T> key, T value);
    <T> WriteResult putIfRevision(DataKey<T> key, T value, long expectedRevision);
    <T> WriteResult update(DataKey<T> key, UnaryOperator<T> updater);
    WriteResult remove(DataKey<?> key);
    <T> Subscription observe(DataKey<T> key, Executor executor,
                             DataChangeListener<T> listener);
    EventBus events();
}

public interface ValueCodec<T> {
    String schemaId();
    int schemaVersion();
    byte[] encode(T value);
    T decode(byte[] payload, int savedSchemaVersion);
}

public final class DataKey<T> {
    StoreType storeType;    // MEMORY / FILE / DATABASE
    DataScope scope;        // DEVICE / USER / USER_CE 等受控作用域
    String namespace;
    String key;
    ValueCodec<T> codec;
}

read() 返回包含 exists、值、revision、服务 epoch 的 DataSnapshot<T>；不存在不能与 boolean false、int 0 或空字符串混淆。put() 是 upsert；要求只创建不覆盖时使用 putIfAbsent()（可通过 CAS=0 实现）。

SDK 推荐默认提供异步调用方式（例如 Executor / Future，Kotlin 扩展可提供 suspend），避免业务在主线程进行磁盘提交或同步 Binder 往返；同步 readBlocking/putBlocking 只允许后台线程调用。回调 Executor 由 App 显式指定。

6.2 在业务 SDK 中定义类型化数据契约

// device-data-sdk.aar：由多个 App 共享、独立版本化
public final class DeviceDataKeys {
    private DeviceDataKeys() {}

    public static final DataKey<Integer> DEVICE_MODE =
        DataKey.of(StoreType.MEMORY, DataScope.DEVICE,
            "sys.device", "device_mode", Codecs.INT);

    public static final DataKey<DeviceConfig> DEVICE_CONFIG =
        DataKey.of(StoreType.FILE, DataScope.DEVICE,
            "sys.device", "device_config", DeviceConfigCodec.INSTANCE);

    public static final DataKey<DeviceConfig> DEVICE_CONFIG_DB =
        DataKey.of(StoreType.DATABASE, DataScope.DEVICE,
            "sys.device", "device_config", DeviceConfigCodec.INSTANCE);
}

6.3 Apps 层只保留业务逻辑

GlobalDataManager global = GlobalDataSdk.connect(context);

// MemoryStore：开机运行期共享值
// 用法示意：后台线程或异步封装调用
WriteResult r1 = global.put(DeviceDataKeys.DEVICE_MODE, 2);
DataSnapshot<Integer> s1 = global.read(DeviceDataKeys.DEVICE_MODE);

// FileStore：跨重启的 DeviceConfig
DeviceConfig config = new DeviceConfig(1001, "Android TV", true);
global.put(DeviceDataKeys.DEVICE_CONFIG, config);

// DatabaseStore：对象数据的另一种独立持久化位置
global.put(DeviceDataKeys.DEVICE_CONFIG_DB, config);

// 修改：SDK 负责读取、执行 updater、CAS 和有限次重试
global.update(DeviceDataKeys.DEVICE_CONFIG, old ->
        old.withEnabled(false)); // 推荐不可变对象返回新值

重要：DeviceDataKeys.DEVICE_CONFIG 与 ...DEVICE_CONFIG_DB 指向两个独立数据对象。SDK 不应在写入 FILE 后自动镜像 DATABASE，也不应让 App 不知情地将 MEMORY 同步到磁盘。

6.4 统一的通用 Store 入口仍保留

业务不需要 Type-safe SDK 时，也可以直接使用 manager.memory("ns")、manager.file("ns")、manager.database("ns") 提供的 putInt/getInt/putObject/observe。推荐对共享业务数据优先使用 DataKey/Repository，对调试与简单 Key 使用通用 Store API。两套 API 最终走同一条传输协议，不应两套服务端实现。

GlobalStore memory = manager.memory("device");
GlobalStore file = manager.file("device");
GlobalStore database = manager.database("device");

memory.putInt("runtime_mode", 2);
file.putObject("startup_config", config, deviceCodec);
database.putObject("user_config", config, deviceCodec);

// 三种 Store 分别订阅，数据不自动互相镜像
Subscription s = memory.observe("runtime_mode", executor, listener);

6.5 关于引用类型实例

服务端托管的是 byte[]，因此返回的 DeviceConfig 是解码后的新对象；saved.enabled = false 不会自动发出通知，必须调用 SDK 的 put/update。不要把 Activity、Context、Thread、Socket、View 等进程内资源塞进 Codec。对于集合、泛型和多态对象，Codec 必须明确具体类型及 schema 演进规则。

07｜传输层 IPC / Bridge：首次系统集成后保持稳定

7.1 通用数据包，不携带业务类

StoreKey      = (storeType, scope, verifiedOwner, namespace, key)
EncodedValue  = (schemaId, schemaVersion, encoding, payloadBytes)
DataSnapshot  = (present, revision, serviceEpoch, EncodedValue?)
ChangeEvent   = (storeType, scope, namespace, key, operation, revision, epoch)
EventMessage  = (topic, scope, eventSequence?, epoch) // 无业务 payload
  • storeType：MEMORY、FILE、DATABASE，不是任意 App 可自定义的第四种类型。
  • scope：设备级 / 用户级 / CE 或 DE 的明确范围；服务端验证用户权限，不能无条件信任客户端填入的 UserId。
  • revision：配合 expectedRevision 完成 CAS；删除也必须推进修订版，避免旧版本误写。
  • serviceEpoch：服务实例变化标识，帮助 SDK 判断 MemoryStore 是否整体丢失及 Observer 是否需要恢复。
  • encoding：例如 primitive-be-v1、json-utf8、proto-v1；Service 只校验边界大小与元数据合法性，不反序列化未知业务类。
  • schemaId/schemaVersion：业务数据格式身份，独立于 Client SDK 的 Maven 版本和 IPC 协议版本。

7.2 冻结的 AIDL 能力（概念性协议）

    void onEvent(in EventAddress address);
}

上述语法为协议草案；真实项目要采用所在 AOSP 分支支持的 AIDL 类型、Parcelable 与生成方式，且 StoreSelector/EventAddress 的用户范围不能造成授权绕过。ServiceCapabilities 至少包含 protocolMajor/minor、feature 位图、支持的三种 Store、最大 payload、支持的用户范围。不要为每个 DeviceConfig 增添 AIDL 方法。

7.3 IPC 错误语义

状态 场景 SDK 行为
NOT_FOUND 第一次读取不存在 / 删除后无值 返回 present=false，仍提供当前 revision
PERMISSION_DENIED 未获授权的读/写/监听/发布 不重试，不用默认值掩盖敏感权限失败
CONFLICT CAS 的 expectedRevision 不匹配 可有界重读重试；禁止无限循环
QUOTA_EXCEEDED 值大小、UID 占用、listener/事件超过预算 返回可诊断的错误，不静默淘汰权威内存数据
UNSUPPORTED SDK 请求旧服务不支持的 feature 能力协商后关闭该功能或降级
LOCKED 用户尚未解锁，访问 CE 数据 等待解锁或返回明确错误，不迁移到 DE 偷存
STORAGE_UNAVAILABLE 文件损坏 / SQLite IO 错误 / 空间不足 失败并记录诊断；不发成功通知
SERVICE_DIED Binder 失联 SDK 发起重连、重新注册 Observer、重新读取快照
TIMEOUT/BUSY 队列饱和或超过执行时限 有界重试、回退与监控；不能阻塞主线程

设计建议：业务 SDK 可把以上错误映射为稳定异常类型或 Result<T>。服务端严禁把原始 SQL 语句、系统路径、栈信息或其他 App 的隐私数据泄露给普通调用方。

7.4 Bridge 如何让普通 App 合法接入

推荐首次修改 AOSP 时提供极小的、正式可见的 OEM 公开 GlobalDataBridge 入口及配套编译 SDK，唯一主要职责是获取版本化的传输 Binder；业务 App 使用 AAR 封装为 GlobalDataManager。不要让普通 App 通过反射调用隐藏 ServiceManager.getService()。Bridge 可按需要进行发现能力的权限检查，但每一次 read/write/subscribe/publish 仍必须在最终服务端按真实 Binder 调用 UID独立验证。

对不方便维护 OEM public Framework API 的设备，可以改用预装受控 ContentProvider / exported BoundService 作为稳定公开网关；其启动时序、组件访问权限和 SDK 使用方式与 Framework Bridge 不同，不能默认为完全等价。两种网关只选一种作为正式产品主路径，避免双通路鉴权与维护。

7.5 版本演进约束

  • 首次发布定义 protocolMajor=1；后续新增可选字段、可选操作采用兼容扩展机制与 feature negotiation。
  • 变更字段语义、删除既有字段、修改原有 byte encoding，必须视为不兼容升级并明确系统更新路径。
  • AIDL 的冻结策略应根据模块与分区边界选择；不应机械地把所有 system_server ↔ App AIDL 标成 @VintfStability。
  • SDK 可升级不代表服务端会突然拥有新事务特性；SDK 只能在现有能力上组合操作，无法凭空提供旧内核没有的跨 Key 原子性。

08｜三种 Backend 的详细设计

8.1 相同的接口，不同的存储语义

interface StorageBackend {
    DataSnapshot read(StoreKey key);
    WriteResult write(StoreKey key, EncodedValue value,
                      long expectedRevision);
    WriteResult delete(StoreKey key, long expectedRevision);
    BackendHealth health();
}

三个 Backend 完全独立。相同 namespace/key 在 MEMORY、FILE、DATABASE 中指向不同数据，不会自动迁移、合并、写回或镜像。StorageRouter 应根据传入类型只选择一个 Backend，任何跨 Store 复制必须使用独立、显式的迁移流程。

维度 MemoryBackend FileBackend DatabaseBackend
权威数据 服务端 Map 中的不可变字节快照 namespace 小型文件快照 SQLite KV 行
App 死亡 数据保留，若服务仍存活 数据保留 数据保留
服务死亡 / 重启 丢失 已确认成功提交的数据可恢复 按声明的事务耐久性策略恢复
写入方式 原子 Map 替换 / CAS 持锁全文件快照 + AtomicFile 单事务 + 索引更新
高频更新 最适合 最不适合 较适合
大量 Key 受服务端内存预算限制 受单文件规模与写放大约束 可索引，较适合
故障分隔 进程内 namespace / 分片文件 数据库文件 / 用户库
典型用途 在线状态 / 当前模式 少量启动参数 / 静态配置 偏好、业务配置、对象集合

8.2 MemoryBackend

建议采用 ConcurrentHashMap<StoreKey, MemoryRecord>，但CAS + revision + 替换必须在同一个原子临界区内（如 compute() 或分段锁）；Entry 保存不可变的编码字节副本，不能保留来自 App 的任意 Java 类实例。禁止使用会无通知自动回收权威 Key 的普通 LRU。

  • 启动时为空；serviceEpoch 每次进程实例启动变化；Memory revision 在新的 epoch 下重新开始。
  • 支持 get/put/delete/putIfRevision；删除保留逻辑 tombstone 或等效的版本记录，避免 ABA。
  • 配额：每调用者 / namespace 的 Key 个数、总字节数、监听数量限制；容量不足显式拒绝。
  • 若将来增加 TTL，应把“缓存自动过期”标为另一种语义或明确提供过期通知，不能悄悄改变原先“只在显式删除前有效”的契约。
  • 内存不足时不能承诺绝对存活至关机；应用应支持重新初始化。

8.3 FileBackend

建议以 verifiedOwner + userScope + namespace 为逻辑单位组织小型文件，禁止使用客户端传入 namespace 直接拼接系统路径；由内部稳定映射或哈希生成文件名。结构建议：magic | formatVersion | namespaceIdentity | lastRevision | records[] | checksum。

/data/system/.../globaldata/file/  [DE 数据示例，具体路径与 SELinux 按分支决定]
  ownerA_user0_device-config.bin
  ownerA_user0_launcher.bin

CE 数据应单独落到对应 user 的 CE 区域；不能简单全部写 /data/system。

文件写入流程：获取 namespace 互斥锁 → 读取最新快照 → 验证 expectedRevision → 构建新快照并更新 tombstone → AtomicFile.startWrite → 序列化完整文件 → finishWrite → 释放互斥锁 → 成功响应并异步发送通知。失败时 failWrite 并保持旧值；任何会影响可靠性的缓存提交策略都必须在 API 中明示。

  • AtomicFile 保证文件替换完整性，但不提供并发文件锁，服务端仍需互斥。
  • 一个 Key 的修改可能重写整个 namespace；设置 namespace 大小上限，避免无界写放大。
  • 维护文件格式版本和数据校验；区分文件级迁移与客户端业务 schema 迁移。
  • 文件损坏时按受控恢复策略返回 STORAGE_UNAVAILABLE / 进入只读，不得静默置空后覆盖旧文件。
  • FileStore 不是“性能一定高于 SQLite”，仅在小数据、低频写入、以文件为单位恢复时有优势。

8.4 DatabaseBackend

采用 SQLiteOpenHelper / SQLite + WAL，首先实现 StoreKey → EncodedValue 形式的通用 KV；v2.1 不提供普通 App 任意 SQL 字符串执行。

CREATE TABLE namespace_revision (
    scope_id TEXT NOT NULL,
    namespace TEXT NOT NULL,
    next_rev INTEGER NOT NULL,
    PRIMARY KEY(scope_id, namespace)
);
CREATE TABLE global_kv (
    scope_id TEXT NOT NULL,
    namespace TEXT NOT NULL,
    k TEXT NOT NULL,
    present INTEGER NOT NULL,
    schema_id TEXT,
    schema_version INTEGER NOT NULL,
    encoding TEXT,
    payload BLOB,
    revision INTEGER NOT NULL,
    PRIMARY KEY(scope_id, namespace, k)
);
CREATE INDEX idx_global_kv_ns
  ON global_kv(scope_id, namespace, present);

本示意中 namespace 的 owner/storeType/user 范围须纳入真实 scope_id。删除时可保留 present=0 的 tombstone 记录；为避免无限膨胀，需要设计有边界的历史版本回收方案，并保证与 CAS 语义一致。next_rev 在同一写事务中递增，防止多个写者取到重复版本。

  • 单 Key 写入、版本递增、删除标记在同一事务中完成；事务成功后才投递通知。
  • 开启 WAL 可以改善并发读写，但SQLite 同一数据库仍然同时只允许一个写者。
  • 明确持久性策略：synchronous=FULL 更偏向掉电持久性；NORMAL 更偏向写入性能，最近提交事务在突然断电时可能回滚。不得只称“WAL=永不丢数据”。
  • 需要执行 Schema 迁移、数据库完整性检查、WAL checkpoint、空间不足处理、数据库级恢复与备份策略。
  • 真正的按业务字段搜索 / JOIN / 排序不是当前通用 KV API 的能力；可在后续通过受控 Collection API 扩展。

8.5 建议的默认策略

MEMORY 承担运行期权威状态；DATABASE 作为一般持久化业务对象的优先选择；FILE 保留为少量、低频、需要独立文件恢复或简洁快照的配置存储。SDK 不应因为对象类型是 String/POJO 就自行偷偷切换 Store；类型与存储介质选择互相正交。

09｜版本、原子修改与一致性契约

9.1 StoreKey 与 revision

StoreKey = (StoreType, userScope, serverVerifiedOwner, namespace, key)。每个 Backend 对这一空间独立维护单调递增的版本。DataSnapshot.present 与 revision 同时返回：不存在时并非永远 revision=0，因为删除后可能有 tombstone 版本。

9.2 三种写入语义

API 语义 并发行为
put(key, value) 无条件 upsert 允许后写覆盖先写；明确标为 last writer wins
putIfAbsent(key, value) 仅当前 present=false 可写入 SDK 读取不存在状态及其 revision 后 CAS；删除后 revision 并非自动归零
putIfRevision(key, value, rev) 比较 rev 再写 冲突返回 CONFLICT；不改变存储、不通知
update(key, updater) SDK 读快照、调用 updater、CAS、有限重试 updater 可能被执行多次，必须无副作用、可重复
delete(key, expectedRevision) 原子删除或标记不存在 写入成功推进 revision；通知 DELETE

9.3 为什么需要 tombstone（防止 ABA）

T0: Key 不存在，revision=0
T1: App1 创建 A，revision=10
T2: App2 删除 A，revision=11（保留 present=false 的 tombstone）
T3: App3 重建 B，revision=12
T4: App1 用 revision=10 再次覆盖 → 必须 CONFLICT

如果删除时彻底抹掉所有版本信息，App1 可能错误地把重新创建的数据当成“从未发生变化”。v2.1 规定：删除与重建不得重置该 Key 可观察的 CAS 历史，除非整个命名空间被管理员显式重置并改变 namespace generation / epoch。

9.4 跨 Store 事务

三种 Backend 分别提交，不承诺 MEMORY + FILE + DATABASE 的跨后端原子事务。例如先写内存再写数据库，数据库失败不能假装两者同时成功。若以后确实需要跨 Store 的事务，应新增明确的服务端能力并升级 IPC；不可只用 SDK 多次 put() 伪装为原子提交。

9.5 一致性与通知次序

同一 Key 的成功写入在 Backend 内按 revision 串行提交；同一 Service 中通知先进入有序队列，再异步调用客户端，不得持文件锁 / DB 事务锁执行远程回调。SDK 对“通知已达”的理解仅是数据已可能改变，读取端以最新 read() 为权威，不依赖每个中间事件恰好送达。

10｜DataObserver：真实数据变更通知

10.1 数据事件结构与触发规则

// 业务 SDK 看到的事件抽象（示意）
record DataChange(
    StoreType storeType,
    DataScope scope,
    String namespace,
    String key,
    ChangeOperation operation, // CREATE / UPDATE / DELETE
    long revision,
    String serviceEpoch) {}

只有 Memory / File / Database 的权威写入成功才发布 DataChange；写入参数错误、权限拒绝、CAS 冲突、文件回滚或数据库回滚不得发成功通知。观察者必须被明确授权观察对应 Key，观察本身可能泄露设备行为；若 SDK 的高级监听接口会自动读取最新对象，则调用者还必须同时具备 READ 权限，仅有 OBSERVE 权限时只能收到不含数据值的失效通知。

10.2 推荐订阅 API

Subscription sub = global.observe(
    DeviceDataKeys.DEVICE_CONFIG,
    context.getMainExecutor(),
    new DataChangeListener<DeviceConfig>() {
        @Override public void onChanged(DataSnapshot<DeviceConfig> latest) {
            render(latest.value());
        }
        @Override public void onResyncRequired(Reason reason) {
            showRefreshState();
        }
    });

// 在生命周期结束时关闭
sub.close();

示例中的 onChanged(DataSnapshot<T>) 由 SDK 接收失效通知后再次读取 实现，系统服务的通知不直接传输业务 Java 对象。若 read() 会访问磁盘或 Binder，SDK 应在后台 executor 拉取快照，再通过指定 executor 分发至 UI。回调顺序由 SDK 排队策略保证，不能假定任意多线程 Executor 自然有序。

10.3 避免初始化读取与订阅之间的竞态

App:   subscribe(key) ──► [服务确认注册] ──► read(snapshot rev=N)
                                          │
Service:  ──────── 写入 rev=N+1 ───────────┘
SDK:   注册已生效后缓存早到的通知；读到快照后，
       按 revision 合并或再读最新值，最后向业务交付。

如果业务先读、再注册，两个操作之间可能出现不会再补发的变更。推荐 SDK 实现 observeAndRead()，或内部采用“先注册 → 获取快照 → 根据 revision/epoch 去重与重同步”的稳定流程；数据通知允许合并，不保证逐个中间版本都触发 UI 更新。

10.4 Binder death 和恢复

Client SDK 监测传输 Binder 死亡：标记所有 Subscription 为需恢复 → 发出 onResyncRequired → 重新获取 Bridge/服务 Binder → 获取 getCapabilities() → 重新注册 → 重新读取所有必要快照。MemoryStore 服务重启后一定应视为全新会话；File/DB 可以恢复提交成功的数据但仍须重新读。

服务端可用 RemoteCallbackList 管理跨进程监听器，负责进程死亡后的清理；还应限制每 UID 监听数量、每次扇出和积压队列。远程回调必须移出 DB/文件锁外执行。

11｜GlobalEventBus：独立的无载荷事件通道

11.1 为什么必须与 DataObserver 分开

项目 DataObserver GlobalEventBus
触发条件 三种 Store 有真实数据提交 App 主动调用 post(topic)
事件与 Key 绑定真实 StoreKey 与三种 Store 完全独立
消息数据 Key、版本与变更元数据 仅 Topic/作用域等元数据，无业务 payload
离线接收 历史变更不补发；可重读最新值 历史事件不补发，也无状态可补读
默认语义 latest-state invalidation best-effort transient signal
典型用途 配置已更新，另一个 App 重新 get 通知其他 App 执行一次刷新动作

11.2 业务 SDK 中定义 Topic

public final class DeviceTopics {
    private DeviceTopics() {}
    public static final EventTopic CONFIG_REFRESH =
        EventTopic.of(DataScope.DEVICE, "com.oem.device/CONFIG_REFRESH");
    public static final EventTopic WAKE_UI_HINT =
        EventTopic.of(DataScope.USER, "com.oem.device/WAKE_UI_HINT");
}

// App1 发送事件
manager.events().post(DeviceTopics.CONFIG_REFRESH);

// App2 监听在线事件，收到后自行做业务刷新
Subscription s = manager.events().subscribe(
    DeviceTopics.CONFIG_REFRESH,
    context.getMainExecutor(),
    event -> refreshLocalUi());

11.3 事件投递契约

  • 不持久化、不重放：服务转发给当前在线且合法注册的订阅者；App 已退出或被冻结不保证收到。
  • 不传业务 payload：topic 是必要的事件路由元信息，不能把它误当成“完全没有字节传递”。
  • 权限区分：PUBLISH 与 SUBSCRIBE 单独授权；Topic owner/namespace 不由客户端自述决定。
  • 顺序：Service 可维护同一 Topic 的发布排队顺序；客户端选择多线程 Executor 时不保证实际执行顺序。
  • 背压：按 UID/Topic 设置速率配额、队列长度与丢弃策略；慢客户端不能拖垮 Service。
  • 边界：支付、远程升级、一次性必须执行的关键命令不能使用此 EventBus 当作可靠消息队列；需要另设计持久任务队列。

11.4 需要重视的安全点

新增 Topic 不需要改 AOSP 仅在其发布/订阅权限落入已支持的规则时成立。任何 App 不应凭自由字符串向 sys.* 保留 Topic 发布事件。对系统保留主题，使用签名权限 / 预配置授权或受控授权数据；对普通 App 主题，服务验证 ownership，跨 App 订阅遵从 owner 授权。

12｜安全架构：身份、ACL、多用户与存储隔离

12.1 为什么客户端 SDK 不能决定权限

SDK 代码运行在 App 进程中，不能作为安全边界。服务端必须从 Binder 获得真实 calling UID，并关联 Android User、包名、签名证书/签名历史及授予的访问范围；不得相信客户端传入的 ownerUid, isSystemApp, isTrusted 等字段。

请求到达
  ↓ 获取真实 Binder caller UID / userId
解析 caller 的受验证 package/signing 身份
  ↓ namespace/topic owner + scope 规则
校验操作 READ / WRITE / DELETE / OBSERVE / PUBLISH / SUBSCRIBE
  ↓ 检查单值大小、配额、速率和解锁状态
选择 Backend 或 EventHub

12.2 Namespace / Topic 权限建议

逻辑范围 默认 READ 默认 WRITE / DELETE 默认 OBSERVE 备注
app.<owner> Owner Owner Owner 私有数据；owner 应验证为包身份而非裸数字 UID
share.<owner> 明确获授予的 App Owner / 显式写授权 单独获授权 可复用系统通用 ACL，无需新增 Key 修改代码
sys.<domain> 按系统签名/白名单 高权限受信任组件 可只授予订阅 不因为业务 SDK 装在 App 内就给系统权限
events.<owner> 不适用 PUBLISH 权限 SUBSCRIBE 权限 Topic 与数据 namespace 规则分开

一个持久 namespace 不能仅以 uid=10056 表示归属：卸载后 UID 可能复用。应使用稳定的 owner 记录绑定经验证的包身份/签名证书，定义卸载、重装、签名轮换、shared UID、多用户迁移策略。若采用可撤销动态授权，必须防止 A 授权 B 后在 B 卸载、签名变更时仍旧授权新装应用。

12.3 Device Encrypted / Credential Encrypted

  • DEVICE + DE：确需开机未解锁访问的设备级配置，由服务端按系统权限控制。
  • USER + CE：与特定 Android 用户相关的敏感状态、偏好和账户数据，用户解锁前拒绝读写。
  • USER + DE：必要的用户早期启动配置，但必须证明锁屏前使用合理。
  • 跨 User/Profile：默认拒绝，除非有独立明确的系统授权；切换用户和工作资料锁定时重新评估读写。

FileBackend 和 DatabaseBackend 必须根据 scope 选择正确目录、数据库或用户分片，而不是统统写到一个系统可直接访问的目录。服务端实现要与目标设备的 FBE 配置对齐。

12.4 威胁模型与控制

可能的滥用 潜在后果 控制措施
非法跨 App 读取 / 订阅 泄露状态或行为信息 Read/Observe 独立 ACL、真实 Binder UID
自称系统 Namespace owner 篡改设备策略 禁止由客户端自填 owner；签名/白名单鉴权
发送超大 payload Binder 事务失败、进程内存压力 最大单值限制、校验 metadata、深拷贝
高频 File/DB 写入 I/O 写放大、阻塞 per-UID 限流、异步 I/O、配额、超时
监听器/事件风暴 队列耗尽、CPU 飙升 订阅配额、背压、溢出告警与重同步
文件名穿越 破坏其他系统文件 禁止直接拼路径、校验 namespace、映射安全文件名
错误对象 Codec SDK 进程崩溃/解析异常 Codec 位于 App，服务不反序列化业务类
恶意旧 App 利用 UID 复用 获取前任 App namespace 持久 Owner 绑定包身份及签名，卸载清理/撤权

13｜AOSP 首次集成与 SDK 独立升级边界

13.1 平台侧的最小改动

首次系统构建需要确定并集成：Bridge 的公开 Java API / SDK stub、IPC 契约、Service 注册/启动、三种 Backend、EventHub、权限模型、service_contexts 及对应 SELinux 规则和分区访问方式。之后增加 Java 模型、DataKey、Repository 或 Topic 不需要改这些代码。

AOSP 可参考 SystemServiceRegistry / SystemServer 注册模式，但不同 Android 分支位置与注解/API txt 管理方式可能变化。要求普通 App 公开访问，需提供正式的定制 OEM SDK 编译桩，不能只声明 @hide 类然后让普通 APK 反射获取。

13.2 分步启动顺序

init / /data 挂载阶段
   └─ system_server 启动，初始化 GlobalDataSystemService
        ├─ 发布 Bridge 可发现的 Binder 入口
        ├─ 初始化 MemoryBackend（空）
        ├─ 初始化 DE File/Database 存储能力
        ├─ 等待用户解锁后启用该用户 CE 存储
        └─ 启动 Observer/EventHub 受控执行器

App 启动 / SDK.connect()
   ├─ 获取固定 Bridge（失败返回 SERVICE_UNAVAILABLE）
   ├─ getCapabilities，缓存协商结果
   ├─ 注册本 App 所需订阅
   └─ 读取快照 / 发送事件

如果服务在某个早期 boot phase 尚不可用，SDK 应返回可诊断的“尚未就绪”而非无期限阻塞。不能假设应用进程的启动时序早于系统存储初始化。

13.3 编译与交付流程

首次 AOSP 发行：包含 Bridge、Service、AIDL、权限与 SELinux
         ↓
冻结 Protocol V1 + 发布 OEM SDK 编译桩 / Client 2.1.0
         ↓
发布 Business SDK v1.0：DeviceConfig / DataKey / Codec
         ↓
App A / App B 构建并安装
         ↓
日后增加 UserConfig / 新 Topic：只发 Business SDK + 新 APK
         └─ 平台镜像与 system_server 二进制保持不变

注意：AAR 不会自动替换其他 APK 内部已编译进去的代码。独立升级意味着可以独立发布，不需要重新编译平台，并非所有设备上的 App 无需更新就立刻享受新版 SDK。采用 Android 动态共享库 APK 是另一种复杂度更高的分发架构，暂不纳入 v2.1 基线。

14｜版本兼容、对象迁移与回滚策略

14.1 三条独立版本线

版本线 示例 维护者 升级目标
IPC Protocol 1.0 / features AOSP 平台团队 兼容旧 SDK，明确能力范围
Client SDK 2.1.0 SDK 团队 API 易用性、监听与错误恢复
Business Schema device.config/v3 业务合同维护者 新旧 App 共享对象字节兼容

不能把 SDK 版本当作 Java 对象的持久化 SchemaVersion；不同 App 可以携带不同的 Client SDK，但读取相同 StoreKey 数据时必须遵守统一的 Schema 契约。

14.2 Schema 演进推荐

  • schemaId 稳定不变；兼容新增字段时，旧版解析器需容忍未知字段，或提供显式兼容编码。
  • 破坏性重命名、字段类型更换、删除必填字段前，应先完成读旧写新与兼容期评审。
  • 如果多个 App 会写同一对象，必须避免“新版写回新字段、旧版读写把未知字段丢弃”的数据丢失；可选择向后兼容的 Proto、保留未知字段、读改写字段补丁或采用单一写者策略。
  • Business SDK 提供针对多版本样本的 Codec 测试：V1 写 / V2 读、V2 写 / V1 读、格式损坏、未知字段及可选字段缺失。
  • 回滚 APK 时，旧版应用能否读已经写入的新版数据必须提前验证；无法保证时采用双 schema 过渡，而不是仅修改 version int。

14.3 兼容矩阵示例

服务协议 Client SDK Business SDK 预期
1.0 2.1.0 device 1.0 基线功能完整
1.0 2.2.0 device 1.2 若只增加业务模型，应完整工作
1.0 3.0.0 device 2.0 SDK 不得隐式使用旧服务不支持的新 IPC；先 capability 检查
1.1 2.1.0 device 1.0 新服务应继续支持旧客户端既有语义

15｜稳定性、运维与容量规划

15.1 初始参数建议（待压测验证，不是实测性能）

项目 评审建议起点 后续验证
单个 EncodedValue 64 KiB 上限 大对象是否需要 ParcelFileDescriptor / SharedMemory 扩展
MemoryStore 每 UID 数 MiB 初始预算 极端对象数量、GC 与系统内存压力
FileStore 单 namespace 数百 KiB 至 1 MiB 的软上限 每次更新写放大、闪存寿命与断电测试
DatabaseStore 按用户或设备范围隔离 WAL 大小、checkpoint、迁移耗时
DataObserver 每 UID 固定配额 系统扇出/回调积压压力
EventBus 每 Topic 固定速率和队列上限 消息风暴下的丢弃可观测性
主线程调用 禁止阻塞性 I/O StrictMode / ANR / Binder 线程池压测

所有数字应按目标设备的内存、存储、Android 版本和客户端规模实测确定。切忌把概念阶段建议当成 SLA。

15.2 必须记录的运维指标

  • 每 Store/namespace 的 Key 总量、占用字节、写入失败数、慢读写耗时分位数（不记录敏感 payload）。
  • Binder 并发、请求队列、权限拒绝、配额拒绝、超时、重试与 CAS 冲突次数。
  • 监听器数、数据通知队列积压、EventBus 发布量、丢弃数及慢监听者数量。
  • FileBackend 各 namespace 更新放大比、校验失败、最近成功提交版本。
  • DatabaseBackend WAL 大小、checkpoint 频率、事务耗时、完整性错误、Schema 迁移结果。
  • 服务进程重启次数、epoch 变化、SDK 重连成功率与重同步次数。

日志必须脱敏：默认仅打印 hash 后的 key / namespace 标识或有权限的调试信息，不能把对象 JSON/Proto 明文写进 logcat。

15.3 故障与恢复决策

事件 Memory File Database App/SDK 处理
App1 进程死亡 保留 保留 保留 App2 已注册可继续使用；死亡 App 订阅被清理
服务进程死亡 立即丢失 重新加载成功提交的文件 依事务同步策略恢复 断线 → 重连 → 重新订阅 → 全量重读
文件写入中断 不受影响 AtomicFile 失败回退 不受影响 返回错误，不能发成功通知
SQLite 事务失败 不受影响 不受影响 回滚 返回 STORAGE_UNAVAILABLE / 具体错误码
用户未解锁 按作用域 CE 禁止 CE 禁止 SDK 返回 LOCKED，监听解锁后重试
配额达到 明确拒绝 明确拒绝 明确拒绝 UI/业务可报告容量错误，不删其他 Key
EventBus 接收方离线 不相关 不相关 不相关 事件不补发；如果必须必达，重新设计持久任务

16｜测试策略与正式验收矩阵

测试环境：至少两种 UID 的普通 App、一个 platform-signed 系统 App、Launcher/SystemUI 的受控测试组件；覆盖重启、不同 Android User、锁定/解锁以及混合 Client/Business SDK 版本。下表对应自动化测试用例编号，均需记录设备与系统构建号。

用例 场景 关键断言
T01 Memory 基本类型跨 App 读写 同 Key 返回最新值，无磁盘记录
T02 Memory POJO 跨 App 读取 解码一致；修改本地对象不自动写回
T03 Memory 服务重启 旧数据消失、epoch 变化
T04 File 基本类型跨重启 恢复提交成功的值
T05 File POJO 跨重启 schema/Codec 解码正确
T06 File 写入中断 旧快照完整，无假成功通知
T07 File 高写频和大文件 正确限额，无长时间阻塞系统线程
T08 DB 基本类型与 POJO SQL KV 存在且读写准确
T09 DB 事务失败 原子回滚、revision 未伪推进
T10 DB Schema 迁移 旧库升级后数据完整
T11 同 Key 两客户端并发 CAS 只允许符合 revision 的写入成功
T12 删除后重建 ABA 旧 revision 不能覆盖新值
T13 三 Store 同名 Key 各 Store 值独立、通知隔离

T17 EventBus topic fan-out 在线授权订阅者都可收到
T18 EventBus 发布不会写存储 三 Backend 均无对应事件 Key
T19 EventBus 离线客户端 无补发、不主动拉起
T20 Topic 越权发布 / 订阅 Permission denied，无事件泄露

T22 CE 用户未解锁 返回 LOCKED，不落到 DE
T23 UID 复用 / App 卸载 不继承旧 App 所有权
T24 新业务 POJO 仅 SDK/APK 更新 system_server 二进制不变、功能正常

T26 新旧 Business SDK 并存 对象读写与回滚按矩阵兼容

门禁：安全、持久化原子性、ACL、重连、版本兼容 T01–T30 未达标时不能宣布 SDK 可面向全部第三方 App 发布。性能阈值需要与目标 SoC 和 App 负载确定，避免“没有实测却承诺毫秒级响应”。

17.1 Code Review 重点

  • Platform Review：只审 Binder 输入校验、权限、生命周期、事务、线程池、SELinux，不讨论具体 DeviceConfig 字段。
  • SDK Review：只审 DataKey 泛型边界、Codec、错误重试、订阅生命周期、兼容能力协商。
  • Business Contract Review：只审对象字段、schemaVersion、回滚与多 App 兼容、Topic 命名。
  • Release Review：只审 OEM SDK 公开性、App 更新覆盖率、Maven 版本锁定及测试报告。
