ARCHITECTURE REVIEW · VERSION 2.0

GlobalData Framework
系统级数据托管与全局事件总线

面向可定制 AOSP 的通用共享数据基础设施：MemoryStore、FileStore、DatabaseStore 三种独立托管存储，类型化 SDK 可随 App 更新，新增 GlobalEventBus 实现不依赖任何真实存储数据的跨进程事件通知。

通用数据托管SDK 脱离系统编译业务模型共享无负载 EventBus权限与版本兼容
版本 2.0 · 评审稿日期 2026-10-16读者 Android Framework / 系统应用 / SDK / 测试 / 安全
01

设计结论与两项升级

V2.0 = 三种托管存储 + 独立事件总线 + 可随 App 更新的类型化 SDK

推荐采用：稳定系统内核 + 可更新客户端 SDK + 独立 GlobalEventBus

第一次集成 AOSP 时固化通用 IPC 的数据读写、订阅与无负载事件 API。此后仅新增/变更业务数据类、Codec、强类型封装及事件主题时，不改 AOSP、system_server 或系统镜像；更新相应 App 中集成的 SDK 即可。

3托管存储Memory · File · SQLite
2独立消息机制数据变更通知 · EventBus
0业务类型的服务端改动按契约扩展，无需修改 system_server
升级 ①

SDK 与 AOSP 解耦

GlobalDataManager 从“编译进 Framework 的业务 API”转为“随 App 发布的 AAR/JAR”。新增 DeviceConfig、UserProfile 等类型，可放在共享契约 SDK 或业务 SDK 中。

前提：AOSP 内保留一个从首版起稳定、公开可调用的 GlobalDataBridge 入口。

升级 ②

无状态 EventBus

增加 post(topic)、subscribe(topic, listener)。不创建 Key、不写内存、不写文件/SQLite，不携带业务负载。

语义：仅给当前在线且完成注册的授权监听者即时转发；非离线消息队列。

不能忽略的边界：若已发布的旧版系统服务完全没有事件发布/订阅和通用数据传输能力，单靠改客户端 SDK 无法凭空添加服务端逻辑。V2.0 需要在首次平台集成时一次性实现这些通用能力；此后新增数据类型与事件主题无需改系统。

基线需求与非目标

区分必须交付、后续增强与明确不保证的行为

ID能力验收要求优先级
R01三种独立存储Memory / File / Database 独立命名空间与生命周期必须
R02统一数据操作create / put / get / update / remove / observe必须
R03基本类型int、long、boolean、float、double、String、byte[]必须
R04引用类型对象、List、Map 等由 SDK 侧 Codec 序列化必须
R05内存语义仅服务进程存活时有效；App 退出不影响必须

R07业务零侵入新增 schema/key/topic 仅 App/SDK 改动必须
R08SDK 独立升级只更新 AAR 所在 App，不更改 AOSP 代码必须
R09变更通知仅对应存储变更成功后通知，附版本信息必须
R10独立事件总线事件无业务 payload，不要求实体 Key 存在必须
R11安全跨 UID / 用户 / 命名空间的读写与订阅 ACL必须
R12失败可见IPC 故障、冲突、解码失败可判断，不静默成功必须
R13协议演进能力协商、向后兼容、版本与回滚必须

定义：“不重新编译系统”指新增业务模型、类型封装或事件主题不必重新编译 AOSP/system_server；更新业务 App/APK 仍是必须的发布动作。如果 SDK 被放进 Framework bootclasspath 或作为不可独立更新的系统镜像模块，这项基线无法成立。
03

V1.0 → V2.0 的架构变更

保留三种托管后端，改变 SDK 的发布方式，并增加不依赖存储的事件通道

维度V1.0V2.0（推荐）
客户端 SDKGlobalDataManager 易被理解为 Framework 内置类拆为系统固定 Bridge + App 独立 AAR；GlobalDataManager 位于 AAR
引用类型由 App 自行定义 Codec允许 SDK/共享契约模块封装 POJO、Codec、Repository，服务端仍完全不认识业务类型
数据存储Memory / File / SQLite三种 Backend 完整保留、互不自动镜像
数据变更由真实 Key 发生修改触发DataObserver 保留，仍以提交成功为前提
业务事件无独立通道EventHub 支持 post/subscribe，不关联 Key 或任何 Backend
系统升级SDK 变更可能触碰 frameworks/base只有首次引入 Bridge/IPC/Service 需要改 AOSP，后续只修改客户端 SDK/APK
版本管理对象 Codec 版本扩展到协议版本、数据 schema 版本、SDK 依赖版本三层

需要冻结的不是“所有 Java 类”，而是“底层能力边界”

系统服务只认识 storageType、namespace、key、byte[]、schemaId、revision、topic 等通用概念；强类型业务 API 永远留在客户端 SDK。

系统层固定组件

  • GlobalDataBridge：框架公开入口，不提供业务对象接口
  • IGlobalDataTransport：稳定 IPC 契约
  • StorageRouter / 3 Backends：完整底层存储
  • EventHub：通用 Topic 路由
  • AccessController：存储与事件权限策略

客户端可变组件

  • GlobalDataManager：开发者友好的封装
  • GlobalStore：统一三后端类型化接口
  • GlobalEventBus：业务事件发布订阅
  • 业务模型 / Codec / 类型化 Repository
  • App 生命周期中的绑定、重连和订阅管理
公开 API 接入：普通第三方 App 不应直接反射调用隐藏的 ServiceManager.getService()。首次 AOSP 集成应提供合法、稳定的公开 Bridge API 和对应 SDK 编译桩；或使用预装受控的 ContentProvider Gateway 作为备选。默认选择前者。
05

客户端 SDK 独立发布与引用类型封装

允许改 SDK 的核心价值：共享业务类、类型化接口和序列化逻辑，但绝不把它们编进 system_server

推荐拆为两层 AAR：globaldata-client.aar（通用 Manager、Store、EventBus）与 globaldata-contracts.aar / device-data-sdk.aar（共享的 Java 模型、Codec、强类型 Repository）。开发小团队也可以合并成一个 AAR，但不要放入 frameworks/base。

开发者最终调用方式（3 个 Store 的 API 一致）

JAVA
// App 内的 globaldata-client.aar；不是 Framework 内置业务类
GlobalDataManager manager = GlobalDataManager.from(context);

GlobalStore memory = manager.memory("com.oem.device");
GlobalStore file = manager.file("com.oem.device");
GlobalStore db = manager.database("com.oem.device");

memory.putInt("online_count", 3); // 开机期间
file.putBoolean("boot_animation", true); // 跨重启文件存储
db.putString("device_alias", "LivingRoom"); // 跨重启 SQLite

int count = memory.getInt("online_count", 0);
boolean enabled = file.getBoolean("boot_animation", false);
String alias = db.getString("device_alias", "unknown");

可以将 Java 业务类放在 SDK 中吗？

可以，而且适合“多个 App 共同使用的数据契约”。例如 DeviceConfig 可以与 Codec 和 DeviceDataApi 一起打包到共享 SDK。新加一个模型或修改接口，仅重新构建并发布依赖它的 APK。

JAVA
// 放在 globaldata-contracts.aar（或 device-data-sdk.aar）
public final class DeviceConfig {
    public int deviceId;
    public String deviceName;
    public boolean enabled;
}

public final class DeviceDataApi {
    private static final ValueCodec<DeviceConfig> CODEC =
            new DeviceConfigJsonCodec();  // JSON / ProtoBuf

    public static void save(GlobalDataManager manager,
                            DeviceConfig config) {
        manager.file("com.oem.device")
                .putObject("device_config", config, CODEC);
    }

    public static DeviceConfig load(GlobalDataManager manager) {
        return manager.file("com.oem.device")
                .getObject("device_config", CODEC);
    }
}

// App1、App2 只需依赖同一业务契约 SDK：
DeviceDataApi.save(manager, config);
DeviceConfig current = DeviceDataApi.load(manager);

Codec 是服务端不可知的契约

服务端仅保存 schemaId、schemaVersion、二进制 payload，不反射加载 DeviceConfig、不执行任意 App 提供的 ClassLoader、也不要求注册每一种业务类。

JAVA
public interface ValueCodec<T> {
    String schemaId();
    int currentSchemaVersion();
    byte[] encode(T value);
    T decode(byte[] payload, int storedSchemaVersion);
}

// SDK 内的通用类型封装：
<T> long putObject(String key, T value, ValueCodec<T> codec);
<T> T getObject(String key, ValueCodec<T> codec);
<T> long updateObject(String key, ValueCodec<T> codec,
                      UnaryOperator<T> updater); // 内部 CAS 重试

适合封装在共享 SDK

  • 多 App 共享 POJO / 枚举 / 常量 Key
  • JSON / ProtoBuf 序列化与迁移逻辑
  • 类型化 Repository，例如 DeviceDataApi
  • 业务 Topic 常量与事件包装方法

必须避免的耦合

  • 把业务 Java 类放入 Framework bootclasspath
  • 让服务端反序列化非受信任 Java 对象
  • 为每新增一个模型增加 AIDL 方法
  • 让新版 SDK 默认要求旧系统不支持的操作码
版本兼容：独立升级 SDK ≠ 所有旧 App 自动采用新版 SDK。各 App 仍需自己更新 APK；共用数据必须维护稳定的 schemaId、独立的 schemaVersion 和兼容解码策略。跨 App 可以使用不同 SDK 版本，但前提是二进制数据契约兼容。
06

三种托管存储的契约与生命周期

三套独立存储空间，同一种业务类型接口，不自动互相镜像

Backend实现方式生命周期与一致性推荐场景
内存 Memory仅服务端进程内存App 退出仍可访问；服务进程死亡、设备重启数据消失高频运行状态、临时共享对象
文件 FileAtomicFile + Proto/二进制 KV写入确认提交后跨重启保留；适合小数据集设备配置、少量业务对象
数据库 SQLiteSQLite + WAL + KV 表事务提交后跨重启保留；可以扩展索引/批处理大量键值、频繁写入、结构化记录

MemoryBackend

服务端 ConcurrentHashMap<StoreKey, Entry> 或分段锁 Map 管理值与版本。即使缓存“引用对象”，实际保存也应是序列化字节的不可变快照，不保留其他 App 的 Java 引用。支持 CAS、按 namespace 配额，服务进程重启后重置内存 epoch。

不提供自动持久化。并非 App 层本地 static 或各 App 独立缓存。

FileBackend

建议以 namespace（或用户+namespace）为单位组织小型二进制 KV 文件，每次变更先写新内容，再用 AtomicFile 安全替换；成功提交后回调。适合少量配置，避免每个 Key 各自创建一个文件，也避免大文件每次重写导致高延迟。

应包含文件格式版本、CRC/完整性校验策略、原子更新锁与升级迁移逻辑。

DatabaseBackend

SQLite + WAL 的通用 KV 表，索引键为 (userScope, namespace, key)，存储类型标识、schema、payload、revision。写入与版本更新在单个事务内完成。

V2.0 的 DatabaseStore 首先保证 KV API。按对象字段过滤、全文检索、联表查询属于可扩展的后续能力；不要直接让 App 向 system_server 提交任意 SQL。

统一数据主键和读写语义

协议示意
StoreKey = (storeType, userScope, namespace, key)
DataEntry = (typeTag, schemaId, schemaVersion, payload,
             revision, updatedAt)

// 创建、修改均走 put；可选 putIfAbsent 和 CAS：
long revision = file.putObject("config", config, codec);
DeviceConfig x = file.getObject("config", codec);
boolean updated = file.compareAndSet(
        "config", expectedRevision, config, codec);
file.remove("config");
一致性规则：memory("device").putInt("x",1)、file("device").putInt("x",2)、database("device").putInt("x",3) 是三条不同记录。修改某一存储只通知该存储上的数据监听者。
读写性能：不建议在 system_server 主线程执行文件或数据库 I/O。普通 App 大量并发写入场景应考虑专用执行器及总量/频率限制；极高风险环境可迁出到独立系统进程，客户端 API 不变。
07

新增 GlobalEventBus：无负载跨进程事件转发

这是独立于数据存储的第四条能力通道，但不是第四种存储后端

⚡

Topic-only Event：post → filter → fan-out

App1 发送一个事件主题；GlobalDataService 检验发布权限后把通知转发给当前已注册、在线且有权限的监听者。事件不会创建 MemoryStore 的 Key，也不创建 File / SQLite 记录。

JAVA
// App1：发布事件，不带业务 payload
GlobalDataManager manager = GlobalDataManager.from(context);
manager.events().post("com.oem.device/CONFIG_REFRESH");

// App2 / App3：注册监听
Subscription sub = manager.events().subscribe(
        "com.oem.device/CONFIG_REFRESH",
        context.getMainExecutor(),
        () -> refreshDeviceUi());

// Activity/Service 生命周期结束时注销
sub.close();
App1post(topic)
GlobalEventBus SDK通用 IPC
EventHub鉴权 / Topic 路由
App2 listener收到回调
App3 listener收到回调
App1 ───────────────→ EventHub ───────────────→ 当前在线的订阅者

真实数据变化 vs 纯业务事件

维度DataObserver（有状态）GlobalEventBus（无状态）
触发前提Memory / File / DB 数据真实写入成功调用 post(topic)，无需真实 Key
业务数据数据存在 Store 中，可 get() 查询不创建或持久化任何业务数据
通知内容storeType、namespace、key、revision 等元数据topic 标识；不携带业务 payload
重启后持久数据可重新读取最新值历史事件不可重放
迟到的监听者读取当前值完成状态同步不会补收已发布事件
用途配置变化、对象更新、缓存状态刷新 UI、触发某次协作动作、内部跨 App 信号

建议的事件语义

  • 主题：com.oem.device/CONFIG_REFRESH，允许新建 topic 而不改系统代码
  • 送达对象：在线、已注册、有权限且未失效的客户端
  • 顺序：同一 Topic 在服务端单队列有序投递；客户端执行顺序受 Executor 影响
  • 失败：进程退出、冻结、积压等可导致事件丢失

禁止混淆的行为

  • post 不会偷偷写一个 event_changed=true 的 KV
  • 无业务 payload 不等于无需权限
  • 不会主动拉起所有处于停止状态的 App
  • 不能把纯事件当支付、订单、升级任务等可靠消息队列
特别说明：如果业务要求“App2 当前没运行，也必须最终收到 App1 发送的事件”，仅用 Binder EventBus 做不到；那是持久化消息/任务队列的需求，应新增 durable inbox 或 Job 机制，已超出本次无状态 EventBus 的定义。

一次性固定 IPC/Bridge：SDK 可更新的必要条件

系统接口必须足够通用且可版本协商，新增模型与 topic 不触碰 service

第一次改 AOSP 时就要提供的能力

get / put / remove统一存储类型与二进制载荷
CAS / revision并发写入与通知次序
data observer真实 KV 变更事件
event publish / subscribe零业务 payload 的 Topic 总线
AIDL · 概念性接口草案
// 核心约定（示意，真实 AIDL 需拆为独立文件）
parcelable DataEnvelope {
    int valueType;
    String schemaId;
    int schemaVersion;
    byte[] payload;
    long revision;
}

interface IGlobalDataTransport {
    int getProtocolVersion();
    DataEnvelope get(int storeType, String ns, String key);
    long put(int storeType, String ns, String key,
             in DataEnvelope data, long expectedRevision);
    long remove(int storeType, String ns, String key,
                long expectedRevision);

    void registerDataObserver(int storeType, String ns,
                              String key, IDataObserver callback);
    void unregisterDataObserver(IDataObserver callback);

    void publishEvent(String topic);
    void registerEventListener(String topic, IEventListener callback);
    void unregisterEventListener(IEventListener callback);
}

oneway interface IEventListener {
    void onEvent(String topic); // 无业务 payload
}

此处代码用于冻结能力边界，不是可直接复制到单个 .aidl 文件的完整构建产物：实际工程必须为 Parcelable、两个 Callback 分别建 AIDL 文件，并依目标 AOSP 分支生成/冻结适用的接口版本。

App 如何合法获取系统 Binder

JAVA · 客户端内部示意
// 仅是客户端侧使用形态示意；GlobalDataBridge 在首次 AOSP 构建时提供。
GlobalDataBridge bridge = context.getSystemService(
        GlobalDataBridge.class);
IBinder binder = bridge.getServiceBinder();

// SDK 内部转换为稳定 IPC 代理（业务 App 不直接处理 AIDL）
IGlobalDataTransport transport =
        IGlobalDataTransport.Stub.asInterface(binder);

GlobalDataManager manager =
        new GlobalDataManager(transport);
首选方案：首次编译系统时，把 GlobalDataBridge 注册为公开可用的 Framework system service，并更新定制 SDK 编译桩；Bridge 只负责返回受控 Binder 入口，所有调用必须由 system_server 再次按 UID/权限校验。以后 Client SDK 作为普通依赖库发布。

稳定协议策略

  • 操作码、字段、类型 ID 首版固定
  • getProtocolVersion() / feature capability 协商
  • 新客户端先校验能力，再使用旧系统已支持的特性
  • 数据 schema 版本独立于 IPC 协议版本

备选 Gateway

  • 若不希望公开自定义 Framework Java API，可首次预装受控的 Provider Gateway
  • AAR 通过 ContentResolver 得到受控 Binder 句柄或使用 Provider API
  • 代价是额外组件、进程路径与 IPC 维护复杂度
关于 Stable AIDL：AOSP 的稳定/版本化 AIDL 是值得参考的兼容性工程方法，但要区分“平台内接口兼容”与跨分区 VINTF 合约；不要因为是 system_server ↔ App 的接口就机械地添加 stability: "vintf"。应根据所在分区、构建模块和分发策略确定具体 AIDL 配置。
09

完整使用流程与两种监听机制

Apps 只操作 SDK；系统服务只传输不透明载荷与事件元信息

方案 A：SDK 封装共享 DeviceConfig

1

App1 引入新版 device-data-sdk.aar；模型、字段、Codec、API 均在 SDK 中。

2

App1 调用 DeviceDataApi.save()，底层选 File 或 SQLite，提交成功后产生 revision。

3

App2 的 DataObserver 被通知；App2 用对应 SDK 版本读取并反序列化。

4

后续新增 DeviceConfig.newField 时升级契约 SDK 和相关 APK；不改 Service。

方案 B：App1 广播一次不带数据的业务事件

1

App2、Launcher 注册 CONFIG_REFRESH 事件监听。

2

App1 调用 post(".../CONFIG_REFRESH")，EventHub 完成发布权限校验。

3

EventHub 只通知匹配 Topic 的在线 listener，没有数据读取/写入动作。

4

接收端决定是否刷新页面、发起业务检查或执行自身操作。

数据变更监听建议 SDK 写法

JAVA
GlobalStore store = manager.file("com.oem.device");

// 先注册，再读取状态，避免“先读后注册”的更新窗口
Subscription sub = store.observe(
        "device_config", context.getMainExecutor(),
        change -> {
            DeviceConfig config = store.getObject(
                    "device_config", DEVICE_CODEC);
            render(config);
        });

DeviceConfig initial = store.getObject(
        "device_config", DEVICE_CODEC);
render(initial);

// onStop / onDestroy: sub.close();
// 重连后 SDK 恢复订阅并提示客户端重新同步。
可靠的状态同步：订阅成功后读取最新状态，SDK 在 Binder death / 重连时重新注册并触发 onResyncRequired；DataObserver 的回调建议只带身份/版本元数据，接收端重新 get。EventBus 则不做“补读”，因为不存在相应状态。

安全、可靠性与生命周期

“全局共享”必须建立在明确授权之上；回调风暴与数据滥用会放大 system_server 风险

作用域示例默认权限语义服务端判断
独立 App 私有app.<appIdentity>仅拥有者读写/订阅按 verified UID+包签名映射
App 共享读public.<appIdentity>拥有者写、受策略允许者读/订阅不允许任意 App 冒名发布事件
系统托管sys.device签名权限或预配置 allowlist可授权普通 App 只读/只订阅
事件 Topiccom.oem.device/CONFIG_REFRESH发布与订阅权限分开遵循作用域/用户隔离

权限与身份

  • 服务端从 Binder 读取调用 UID，不信任 App 自填 ownerUid
  • 发布权限与订阅权限独立；监听本身也可能泄露业务状态
  • 按 Android User/Profile 隔离，跨用户仅明确授权后开启
  • Shared UID、包卸载/重装、签名变更要纳入所有权迁移规则

资源与拒绝服务控制

  • 每 UID 的总存储空间、单条 value 大小限制
  • 每 UID 注册的 DataObserver / EventListener 数量配额
  • 每 Topic 的发布速率、队列长度和投递预算
  • 从 Binder 工作线程异步投递回调，不在持有数据库锁时执行客户端逻辑

四种不同生命周期不可混淆

项目App 进程终止system_server 意外死亡 / 系统重启再次启动处理
MemoryStore保留（服务仍存活时）丢失重新初始化；新的 boot/session epoch
FileStore保留已确认提交的数据保留重新加载文件 / 恢复订阅
DatabaseStore保留已确认提交的数据保留重新打开 SQLite / 恢复订阅
GlobalEventBus 订阅与历史事件订阅消失；历史事件不保留全部消失重新注册；无历史回放
可交付语义：“开机到关机的内存对象”准确表述为“服务进程生命周期内临时托管”。事件总线默认 best-effort、非持久、非离线必达。这两条约束应写进 SDK API 文档。

变更对构建产物的影响矩阵

变更类型需要重编 AOSP？需要更新 App/SDK？备注
首版部署 V2.0 系统服务是是首次集成包含三个 Backend + EventHub + Bridge + ACL + SELinux
新增 int/string Key否是APP 调用现有 put/get/observe
新增 DeviceConfig Java 模型否是更改共享模型/Codec 和目标 APK
修改 DeviceConfig 字段否是版本化 schema，兼容旧 App 读取
新增 EventBus Topic否是权限范围已允许的新主题，无服务注册表硬编码
为现有 Topic 新增监听 App否是授权后注册事件回调
更改 SDK 的类型化 Repository否是只影响链接该 SDK 的 APK
新增第四种 Backend / 新 IPC 操作通常是是超出冻结的能力边界，需要系统升级
改变系统 namespace 权限策略可能是视策略而定若 ACL 已数据驱动可不改服务；否则需要平台更新
交付策略：首次发布定制系统时集成公开 Bridge、通用 AIDL、Memory/File/Database、DataObserver、EventHub 及安全策略；客户端 SDK 使用 Maven/AAR 随各 App 构建发布，而不是作为不可更新的 Framework Java 类。

对于 Settings、Launcher 等预装系统应用，是否能“只更新 APK”取决于你的 ROM 升级机制、签名、权限和安装分区安排。允许独立替换 APK 的部署方式可以免 AOSP 全量重新编译；不能独立升级的镜像内置组件仍需走系统发布流程。
